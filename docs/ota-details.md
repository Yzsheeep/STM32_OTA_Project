# OTA 实现与验证记录

[返回项目首页](../README.md)

基于 STM32F103C8T6、JDY-31、W25Q64 和 AT24C02 实现的固件升级项目。电脑通过蓝牙虚拟串口发送固件，STM32 将固件暂存到外部 Flash，完成整包 CRC32 校验后，再擦除并写入内部 APP 分区。

项目采用 **Bootloader + 单 APP 分区 + 外部固件暂存区**，支持从运行中的 APP 发起升级，也可以通过 CH340 使用有线串口升级。这里的 Bootloader / APP 分区不代表双 APP A/B 方案；当前没有自动回滚功能。

## 已实现功能

- APP 接收 `U` 指令，保存升级标志并复位，进入 Bootloader 等待升级。
- Python 上位机下载 GitHub Release 固件或选择本地 `.bin`，通过串口或 JDY-31 蓝牙透传发送。
- 根据 GitHub 上的版本清单比较设备版本；下载后检查文件大小、CRC32 和固件内的版本标识。
- 每包最多 128 字节，采用发送一包、等待字符应答的停等方式。
- W25Q64 暂存完整固件，AT24C02 保存升级标志、固件长度、CRC32 和版本字段。
- EEPROM 元数据写入后读回比较；当前采用逐字节读取方式。
- 搬运前重新读取暂存固件并计算 CRC32，校验失败时退出，不执行 APP 擦除。
- 暂存校验通过后擦除并搬运到内部 Flash，再对内部 APP 执行整包 CRC32 校验；通过后才保存正常启动标志并复位。
- APP 擦除函数向主循环返回执行状态，擦除失败时退出安装，不继续搬运。
- APP 支持 `V` 指令查询自身版本；上位机打开串口时查询，升级后再次查询并与目标版本比较。Bootloader 忽略单字节 `V`，避免将查询指令当作固件写入。

## 硬件与接线

| 模块 / 用途 | STM32 引脚 | 连接说明 |
| --- | --- | --- |
| USART1 发送 | PA9 | 连接 JDY-31 RXD，或 CH340 RX |
| USART1 接收 | PA10 | 连接 JDY-31 TXD，或 CH340 TX |
| W25Q64 CS | PA4 | 片选 |
| W25Q64 CLK | PA5 | SPI1 SCK |
| W25Q64 DO | PA6 | SPI1 MISO |
| W25Q64 DI | PA7 | SPI1 MOSI |
| AT24C02 SCL | PB10 | I2C2 时钟 |
| AT24C02 SDA | PB11 | I2C2 数据 |
| 板载 LED | PC13 | 用于观察 APP 运行及升级后的闪烁变化 |
| ST-Link | SWDIO / SWCLK / GND | 首次烧录与在线调试 |

所有模块需要共地。STM32 通信引脚使用 3.3 V 电平，模块供电按实际模块规格连接。使用 JDY-31 时，断开 CH340 的 TX/RX，避免两个发送端同时驱动 STM32 RX。

串口参数：**9600 bps、8 数据位、无校验、1 停止位**。Windows 与 JDY-31 配对后，在上位机中选择对应的蓝牙虚拟 COM 口。

## 存储布局

| 区域 | 地址 | 大小 / 用途 |
| --- | --- | --- |
| 内部 Bootloader | `0x08000000`～`0x08003FFF` | 16 KB，升级与启动逻辑 |
| 内部 APP | `0x08004000`～`0x0800FFFF` | 48 KB，应用运行区 |
| W25Q64 固件暂存 | 从 `0x000000` 开始 | 接收待安装的 `.bin` |
| AT24C02 元数据 | `0x00`～`0x0F` | 16 字节，保存升级信息 |

**当前升级文件请限制在 16 KB 以内，且长度为 4 字节的整数倍。** `E` 指令目前固定擦除 W25Q64 的前 4 个扇区，即 `0x000000`～`0x003FFF`；内部 Flash 写入函数也尚未处理不足 4 字节的尾部。虽然 APP 分区和部分长度检查允许 48 KB，但当前升级流程尚未完整支持这一上限。

## 升级流程与协议

```text
运行中的 APP
    ↓ U：保存升级标志并复位
Bootloader 等待升级
    ↓ H：握手并保存 16 字节元数据
    ↓ E：擦除外部暂存区
    ↓ 固件分包：每包最多 128 字节，等待字符 '0'
    ↓ C：读取暂存固件，计算整包 CRC32
    ├─ 不一致：输出 CRC check failed，保留原 APP，等待处理
    └─ 一致：擦除 APP（失败则退出）→ 搬运固件 → 校验内部 APP 的 CRC32
        ├─ 不一致：输出 APP CRC failed，保留升级标志，停留 Bootloader
        └─ 一致：清升级标志 → 复位启动 APP → 查询并显示 APP 版本
```

| 上位机发送 | 设备行为 / 应答 |
| --- | --- |
| `U` | APP 保存升级标志并复位；若已在 Bootloader 中，则设置升级标志并输出 `Set Flag OK!` |
| `H` | Bootloader 回复小写 `h`，准备接收元数据 |
| 16 字节元数据 | 写入 EEPROM 并读回比较，成功回复大写 `H`，失败回复 `N` |
| `E` | 擦除暂存区并将写入地址归零，流程结束回复 `E` |
| 固件原始字节 | 每包最多 128 字节，写入调用结束后回复字符 `0` |
| `C` | 校验暂存固件，擦除并搬运后再次校验内部 APP；通过后保存标志并复位 |
| `V` | APP 回复自身版本，例如 `APP_VERSION=1.0.1\r\n`；Bootloader 忽略该单字节指令 |

注意：数据应答是 ASCII 字符 **`'0'`（`0x30`）**，不是数值 `0x00`。128 字节是上位机发送分包大小；设备计算 CRC、搬运固件时使用的 256 字节缓冲区是另一层处理单位。当前没有实现 `J` 指令。

### 元数据格式

上位机按小端顺序发送 4 个 `uint32_t`，共 16 字节，与 `OTA_MetaInfo_t` 对应。

| 字节偏移 | 字段 | 含义 |
| --- | --- | --- |
| 0～3 | `ota_flag` | `0x55AA55AA` 表示升级，`0x00000000` 表示正常启动 |
| 4～7 | `firmware_size` | 固件实际字节数 |
| 8～11 | `firmware_crc32` | 上位机计算的整份固件 CRC32 |
| 12～15 | `version` | 按主、次、修订号编码，例如 V1.0.1 对应 `0x00010001` |

CRC32 初始值为 `0xFFFFFFFF`，采用反射多项式 `0xEDB88320`，结束后异或 `0xFFFFFFFF`，与 Python `zlib.crc32()` 的结果一致。设备校验的是 **从 W25Q64 实际读回的固件**，不是只对串口接收缓冲区计算。

搬运后使用相同参数和实际固件长度，直接读取内部 APP 分区再计算一次 CRC32。两次校验都与元数据中的期望值比较，分别检查暂存数据和安装结果。第二次校验失败时，旧 APP 已被擦除，当前流程不能恢复旧固件。

上位机从 `.bin` 中已有的 `APP_VERSION=x.y.z` 字符串读取目标版本，并生成元数据中的 `version`；云端固件还需与版本清单一致。界面上的设备版本以 APP 对 `V` 指令的实际回复为准。版本比较由上位机完成，Bootloader 尚未据此拒绝降级。

## 目录与技术栈

```text
boot/                      Bootloader 固件，包含 SPI Flash、EEPROM 与升级逻辑
  MDK-ARM/boot.uvprojx      Keil Bootloader 工程
app/                       APP 固件，包含 LED 演示、U 升级请求及 V 版本查询
  MDK-ARM/app.uvprojx       Keil APP 工程
ota_gui.py                 Python 图形上位机
firmware/latest.json       云端版本清单
README.md                  项目说明
```

- **固件**：C、STM32CubeMX、STM32 HAL、Keil MDK / ARMCC、Cortex-M3 向量表与启动跳转。
- **外设通信**：USART1 中断接收 / 空闲中断、SPI1 外部 Flash、I2C2 EEPROM、JDY-31 蓝牙串口透传。当前项目未使用 UART DMA 或 RTOS。
- **数据完整性**：EEPROM 写入读回比较、擦除前暂存固件 CRC32 校验、搬运后内部 APP CRC32 校验。
- **上位机与分发**：Python、Tkinter / ttk、pyserial、requests、HTTPS / JSON、GitHub Releases，使用 `uv` 运行。
- **调试与版本管理**：ST-Link / SWD、Keil 断点与变量观察、Git。

## 编译与使用

### 1. 编译固件

1. 使用 Keil 打开 `boot/MDK-ARM/boot.uvprojx`，按 `F7` 编译 Bootloader。
2. 打开 `app/MDK-ARM/app.uvprojx`，按 `F7` 编译 APP，生成 `app/MDK-ARM/Objects/app.bin`。
3. 工程的 After Build 使用 `fromelf` 导出 `.bin`，其中工具路径需要与本机 Keil 安装位置一致。

当前 Keil 工程使用 ARMCC 工具链，APP 的链接起始地址与向量表偏移均按 `0x08004000` 配置。

### 2. 首次安装

通过 ST-Link，在 Bootloader 工程按 `F8` 下载 Bootloader，再用上位机安装 APP。没有有效 APP 时，Bootloader 会输出 `No Valid App!`，随后可以接收升级指令。

更新 Bootloader 或进入调试前，请检查下载与擦除设置，使用按需扇区擦除，避免全片擦除已有 APP。调试已安装的 OTA 固件时，也应检查 `Update Target before Debugging`，避免进入调试时自动下载覆盖板上内容。

### 3. 启动上位机

在仓库根目录的 PowerShell 中运行：

```powershell
uv run --with pyserial --with requests python ota_gui.py
```

1. 选择有线串口或蓝牙虚拟 COM 口，使用 `9600` 波特率并打开串口，等待 APP 返回实际版本。
2. 保持 Mock 模式关闭，点击“检查云端更新”，有新版本时使用云端下载的固件。也可选择本地 **`app/MDK-ARM/Objects/app.bin`**，不要误用根目录中可能遗留的旧文件。
3. 点击升级，等待元数据、擦除、分包发送、CRC32 校验及搬运流程。
4. 上位机收到 APP 启动提示后自动发送 `V`，回复版本与目标一致后显示“APP 启动已确认”和设备版本。
5. 观察实际 APP 行为，例如修改 LED 闪烁间隔后，确认升级后的闪烁速度变化。

日常更新只需重新编译 APP，再通过蓝牙发送新的 `.bin`，无需通过 ST-Link 直接下载 APP。串口助手与上位机不能同时占用同一个 COM 口。

上位机不保存上次连接的版本；每次打开串口都发送单个 `V` 重新查询。未收到完整回复时显示查询失败，不使用旧版本代替。Bootloader 中已添加忽略 `V` 的分支，使用新版上位机前需先更新 Bootloader。

### 云端分发

默认更新源是仓库中的 [`firmware/latest.json`](../firmware/latest.json)，通过 GitHub Raw 的 HTTPS 地址读取；固件放在对应版本的 GitHub Release 附件中，无需独立后端。清单包含版本号、下载地址、文件大小、CRC32 和更新说明。

设备版本已查询时，上位机只在云端版本更高时下载；版本相同时显示已是最新版本。版本未知时仍可下载核验固件，但不会声称发现新版本。下载内容必须与清单的大小、CRC32 及版本一致，升级后还会核对 APP 实际回复的版本。

发布新版本时，先修改 APP 的版本字符串并编译，再上传对应 `.bin` 到 Release，同步更新清单。仅修改 Release 标题不会改变固件实际版本。Mock 模式保留作本地演示，默认关闭。

## 已完成的实板验证

以下为当前开发过程中的人工实板验证记录，不代表长期可靠性测试。

| 验证项 | 观察结果 |
| --- | --- |
| CH340 有线升级 | 固件发送、搬运后 APP 恢复闪烁 |
| 暂存 CRC32 正常 / 失败路径 | 正常值与期望值一致；人为修改运行时 CRC 后，进入失败分支并跳过 APP 擦除 |
| 搬运后 CRC32 正常 / 失败路径 | 内部 APP 的 CRC 与期望值一致时恢复运行；人为修改运行时 CRC 后，跳过清标志和复位，随后可重新升级恢复 |
| EEPROM 元数据 | 使用逐字节读取后，观察到版本字段及 CRC 字段与发送值一致 |
| JDY-31 蓝牙升级 | 通过蓝牙虚拟串口完成 128 字节停等发送，升级后 APP 运行 |
| 新 APP 生效 | 将 LED 翻转间隔从 1000 ms 改为 200 ms，仅通过蓝牙升级，观察到闪烁加快 |
| APP 版本查询 | 串口助手发送单个 `V`，收到 `APP_VERSION=1.0.0` |
| 上位机自动确认 | 11684 字节固件、92 个分包发送完成后，收到 APP 启动提示及版本回复，界面显示 V1.0.0 |
| 云端下载与蓝牙安装 | 真实下载 GitHub Release V1.0.1 固件，大小 11684 字节、CRC32 为 `1577877E`；92 包发送后设备启动并回复 `APP_VERSION=1.0.1` |
| 重新连接与版本比较 | 重启上位机后连接串口，自动查询 V1.0.1；再次检查云端显示已是最新版本 |

## 当前边界与后续改进

- **确认范围**：上位机依据本轮 APP 启动提示及版本应答确认程序启动，实际版本需与目标一致；版本字符串由 APP 编译时定义，不能替代全部业务功能验证。
- **Flash 错误处理**：已处理 APP 擦除失败返回值，并通过搬运后 CRC 检查安装结果；逐次处理内部 Flash 编程错误、EEPROM 标志保存失败等路径仍待完善。
- **断电恢复**：当前是单 APP 方案，擦除 / 搬运期间断电可能导致 APP 不完整；尚未实现旧固件备份、自动回滚或完整断电恢复验证。
- **驱动与传输**：部分 Flash 操作使用固定延时，错误返回处理尚未完善；数据包没有序号、独立 CRC 或自动重传。字符 `0` 应答表示写入调用结束，不代表该包已经读回核验。
- **版本与安全**：元数据与固件内版本已联动，但暂未实现设备端防降级；CRC32 用于检测数据损坏，不提供固件身份认证或加密。云端清单 CRC32 错误时的拒绝升级路径尚待人工验证。
- **容量扩展**：后续可按固件长度擦除暂存扇区，并补齐写入边界处理，再验证更大固件。
